# Codex Bridge 桌面端设计

状态：提案  
更新时间：2026-08-14  
适用项目：IM Codex Bridge

## 1. 背景

IM Codex Bridge 当前以后台服务运行，将企业微信和飞书消息转发给本地 Codex App Server，并负责访问控制、任务路由、项目切换、审批、消息幂等和结果回传。

现有配置主要通过 `~/.codex-bridge/bridge.toml` 和环境变量维护，运行状态依赖命令行与日志观察。随着接入渠道、项目和使用人数增加，管理员需要一个更直观且安全的本地控制面，用于完成配置、任务观察、审批和诊断。

桌面端不取代企业微信、飞书或 Codex，而是为 Bridge 提供本地管理与审计界面。

## 2. 产品定位

桌面端定位为：**本地 Codex 团队任务控制台**。

- 企业微信和飞书负责发起需求、补充信息和接收结果。
- Codex 负责任务理解、项目工作和最终答复。
- Bridge 桌面端负责连接管理、运行观察、任务追踪、敏感操作审批、安全配置和故障诊断。

桌面端不是完整 IM 客户端，也不用于监控与 Codex 无关的员工聊天。

## 3. 目标与非目标

### 3.1 目标

1. 将首次安装和渠道接入变成可验证的引导流程。
2. 让管理员快速判断 Bridge、适配器和 Codex 是否正常工作。
3. 统一查看经过 Bridge 的 Codex 任务、状态、最终结果和关键事件。
4. 通过原生通知和审批中心处理高风险操作。
5. 用结构化界面安全管理项目目录、渠道 ACL 和运行策略。
6. 在不泄露凭据和敏感内容的前提下提供诊断能力。

### 3.2 非目标

1. 不同步或展示企业微信、飞书中的完整聊天历史。
2. 不提供通用团队聊天、联系人、日历或文档协作能力。
3. 不展示 Codex 的隐藏分析过程或思维链。
4. 不将桌面 UI 作为绕过项目路径、ACL 或审批策略的后门。
5. 第一阶段不支持远程管理其他机器上的 Bridge 实例。
6. 第一阶段不在桌面端实现完整 Codex 对话编辑器。

## 4. 用户与核心场景

### 4.1 Bridge 管理员

- 安装并启动 Bridge。
- 连接企业微信或飞书机器人。
- 配置可访问用户、群聊和审批管理员。
- 添加可信项目，验证路径是否位于允许的根目录内。
- 处理生产变更或其他高风险操作的审批。
- 排查消息未响应、项目路由失败或适配器断连。

### 4.2 项目维护者

- 查看与自己项目有关的 Codex 任务。
- 确认任务是否完成及最终结果。
- 了解任务为何等待输入、审批或重试。
- 在授权范围内继续任务或打开对应 Codex 任务。

### 4.3 普通 IM 使用者

普通使用者主要留在企业微信或飞书中操作。桌面端不是其必要入口。

## 5. 产品原则

### 5.1 任务优先，而非消息优先

界面的主对象是 Codex 任务。来自 IM 的消息、项目切换、审批和最终回复都作为任务时间线中的事件展示。

### 5.2 本地优先

配置、状态和索引默认只保存在运行 Bridge 的本机。桌面端不引入新的云端控制服务。

### 5.3 默认最少暴露

只展示完成管理工作所需的信息。凭据、认证文件、原始环境变量、隐藏分析和未脱敏工具输出不进入 UI 或诊断包。

### 5.4 安全规则只有一个来源

桌面端必须复用 Rust Core 的路径验证、ACL、审批和配置校验逻辑，不能在前端复制一套较弱的判断。

### 5.5 状态必须可解释

不能只显示“失败”。应指出失败发生在渠道、Bridge、Codex、项目路由、审批还是回传阶段，并给出安全的修复动作。

## 6. 信息架构

桌面端采用侧边栏导航：

1. **总览**：服务状态、今日任务、待审批、渠道健康和最近异常。
2. **任务**：经过 Bridge 的 Codex 任务列表、筛选和时间线详情。
3. **审批**：待处理、已批准、已拒绝和已过期的审批记录。
4. **项目**：可信项目目录、路由描述和允许的根目录。
5. **连接**：企业微信、飞书及后续适配器的连接配置与健康状态。
6. **权限与安全**：用户、群组、审批管理员、模型策略和操作守则。
7. **诊断**：组件健康、脱敏日志、消息重试、配置自检和诊断包。

系统托盘提供服务状态、启动/停止、待审批数量、打开主窗口和退出入口。

## 7. 功能设计

### 7.1 首次启动与接入向导

首次启动按以下顺序完成：

1. 检查 Codex CLI、登录状态、Node.js 和本地目录权限。
2. 选择 Bridge 配置目录，默认使用 `~/.codex-bridge`。
3. 添加至少一个允许的工作区根目录。
4. 添加第一个可信项目。
5. 连接企业微信或飞书机器人。
6. 配置渠道 ACL 和至少一名审批管理员。
7. 运行端到端测试消息，确认收取、路由、Codex 回应和回传均正常。

向导中的每一步都必须可重新检查。检查失败时保留已完成配置，不要求从头开始。

### 7.2 总览

总览回答三个问题：

- Bridge 当前是否可用？
- 是否有任务或审批需要处理？
- 最近是否发生影响消息处理的异常？

首版展示：

- daemon、Codex App Server 和各适配器的健康状态；
- 今日收到的消息数、运行中任务数和待审批数；
- 最近任务及其来源、项目和状态；
- 最近错误及建议动作；
- 当前版本和配置更新时间。

不在总览堆叠长期趋势图。趋势与容量统计属于后续版本。

### 7.3 任务与聊天记录

#### 7.3.1 展示范围

桌面端只展示已经经过 Bridge 的 Codex 任务记录，包括：

- 用户发送给机器人的原始请求；
- Bridge 接收到的引用文本；
- 已提交给 Codex 的图片缩略图；
- 来源平台、会话类型、脱敏后的会话标识和发起人；
- 路由到的项目及项目切换事件；
- Codex 对用户可见的回复；
- 澄清、审批、取消、重试和失败事件；
- 任务状态、开始时间、结束时间和最终结果。

桌面端不展示：

- 群聊中未提及机器人的其他消息；
- 平台上的完整历史聊天；
- Codex 隐藏分析、内部计划和思维链；
- 未脱敏的命令输出、环境变量、令牌或认证文件；
- Bridge 没有接收过的引用上下文。

#### 7.3.2 数据来源

- Codex 任务正文优先通过 App Server 的 `thread/list` 和 `thread/read` 获取。
- Bridge SQLite 保存任务索引、IM 路由、关键事件和查询所需的最少元数据。
- 不默认在 SQLite 中复制保存完整 Codex 对话正文。
- 若 App Server 中的任务不可用，列表仍可显示任务索引和失败原因，但不能伪造正文。

#### 7.3.3 列表能力

首版支持按以下条件筛选：

- 状态：运行中、等待输入、待审批、已完成、失败、已取消；
- 平台：企业微信、飞书；
- 项目；
- 时间范围；
- 发起人或任务标题。

默认只展示当前配置允许管理的本机任务。搜索索引不得包含凭据和隐藏分析。

#### 7.3.4 任务详情

任务详情采用时间线，事件类型包括：

- 收到用户消息；
- 创建或恢复 Codex 任务；
- 选择或切换项目；
- 等待用户澄清；
- 等待管理员审批；
- 审批决定；
- 最终回复已发送；
- 回传失败或重试；
- 任务取消或异常结束。

允许的操作包括：

- 复制最终结果；
- 打开对应 Codex 任务；
- 对可重试的回传失败执行一次重试；
- 取消当前仍在运行的任务；
- 在明确展示目标 IM 会话后发送补充消息。

“发送补充消息”属于后续增强功能。首版可以只提供“在来源 IM 中继续”和“打开 Codex 任务”。

### 7.4 审批中心

审批中心集中处理 Bridge 已收到的结构化审批请求。

每张审批卡必须展示：

- 风险类别；
- 发起人和来源会话；
- 精确目标；
- 有限范围；
- 预期影响；
- 恢复或回滚方案；
- 审批所覆盖的全部步骤；
- 过期时间；
- 关联任务和项目。

交互规则：

1. 只有当前渠道配置中的审批管理员可以批准或拒绝。
2. 桌面端批准与 IM 卡片批准使用同一后端令牌和单次消费机制。
3. 任意一端处理后，另一端立即显示最终状态。
4. 过期、重复或无权限操作必须失败关闭。
5. 批准只覆盖卡片列出的单次操作，不创建会话级永久授权。
6. 桌面端不得提供“以后全部允许”选项。

收到审批时发送系统通知。通知正文只显示必要摘要，完整范围需要解锁桌面端后查看。

### 7.5 项目管理

项目页用于管理可信项目目录，而不是任意浏览本机文件系统。

项目字段：

- 稳定且唯一的项目 ID；
- 展示名称；
- 路由描述；
- 规范化后的本地路径；
- 校验状态；
- 最近一次被路由的时间。

创建或修改项目时：

1. 目录必须已存在。
2. 路径必须 canonicalize。
3. 最终路径必须位于 `codex.allowed_roots` 之一。
4. 未知 ID、重复 ID、越界路径和符号链接逃逸必须被 Rust Core 拒绝。
5. 配置文件持久化成功后才能更新运行时目录。
6. 不允许删除最后一个项目。

项目页提供“测试路由描述”功能，但测试只能给出建议项目，不直接切换真实 IM 会话。

### 7.6 连接管理

每个适配器以独立连接展示：

- 名称与平台；
- 启用状态；
- 脱敏后的 Bot/App 标识；
- 进程状态、最近心跳和最近消息时间；
- ACL 摘要；
- 连接测试结果；
- 重启适配器操作。

新增连接采用平台专用向导。凭据优先保存到系统钥匙串，运行时按需注入适配器进程。UI、日志、SQLite 和诊断包均不得保存明文凭据。

为兼容现有部署，首版继续支持环境变量和 `.env`，但界面应明确标注其安全性与来源，不读取或展示实际值。

同一 Bot ID 只允许一个活动的企业微信连接。配置保存前进行冲突检查。

### 7.7 权限与安全

权限配置按适配器隔离，避免企业微信 ID 与飞书 ID 混用。

界面分别管理：

- 允许的私聊用户；
- 允许的群聊；
- 是否允许所有用户或群聊；
- 审批管理员；
- 允许的工作区根目录；
- Codex 模型、Provider 和推理强度；
- operator guardrail 和项目路由提示词。

高风险文本配置应使用“高级设置”区，并提供：

- 修改前后差异；
- 保存前校验；
- 明确的重启影响提示；
- 最近一次有效配置恢复；
- 变更审计记录。

界面不得提供关闭路径边界、绕过 ACL 或将普通用户临时提升为审批管理员的快捷开关。

### 7.8 诊断

诊断页分层显示：

1. 桌面壳与后台服务；
2. Codex App Server；
3. Node.js 与各适配器进程；
4. SQLite 状态库；
5. 企业微信和飞书连接；
6. 配置、项目目录与文件权限。

支持的动作：

- 重新运行配置自检；
- 重启单个适配器；
- 重启 Bridge 服务；
- 查看按组件过滤的脱敏日志；
- 对明确标记为可重试的出站消息重试；
- 导出诊断包。

诊断包默认包含版本、操作系统、组件状态、脱敏配置摘要和有限时间范围的脱敏日志。不得包含 Bot Secret、访问令牌、Codex 认证文件、用户图片和完整任务正文。

### 7.9 系统托盘与原生通知

关闭主窗口时 Bridge 默认继续在托盘运行。托盘菜单包含：

- 当前状态；
- 打开控制台；
- 待审批数量；
- 启动或停止 Bridge；
- 退出。

原生通知用于：

- 新的待审批操作；
- 渠道持续断连；
- Codex App Server 无法启动；
- 配置失效导致服务停止。

普通任务完成默认不发送桌面通知，避免与 IM 回执重复；可在设置中按项目启用。

## 8. 关键用户流程

### 8.1 处理审批

```text
IM 用户发起请求
  → Codex 完成安全分析和准备
  → Bridge 收到结构化审批请求
  → IM 卡片与桌面审批中心同时显示
  → 审批管理员在任一端批准或拒绝
  → Bridge 校验身份、范围、时效和单次消费状态
  → Codex 继续执行或终止
  → 两端同步最终状态
```

### 8.2 查看任务记录

```text
管理员打开任务列表
  → Bridge 查询本地任务索引
  → 选择任务
  → 桌面端通过 App Server 读取任务正文
  → 合并 Bridge 关键事件形成时间线
  → 展示对用户可见的消息、状态和最终结果
```

### 8.3 修改项目配置

```text
管理员选择本地目录
  → Rust Core canonicalize 路径
  → 检查 allowed_roots 与项目 ID
  → 写入临时配置并完整校验
  → 原子替换 bridge.toml
  → 更新运行时项目目录
  → 记录不含敏感值的配置审计事件
```

## 9. 技术架构

### 9.1 推荐方案

推荐使用 **Tauri 2 + 现有 Rust Core**：

```text
Tauri Desktop UI
  ├─ Command API：配置、查询、审批、诊断
  ├─ Event Stream：任务、连接、审批、日志状态
  └─ System Integration：托盘、通知、钥匙串、单实例
          │
          ▼
Bridge Runtime
  ├─ bridge-core
  ├─ StateStore / ProjectCatalog
  ├─ Codex App Server Client
  └─ Adapter Supervisor
          │
          ├─ WeCom Node Adapter
          └─ Feishu Node Adapter
```

选择 Tauri 的原因：

- 可直接复用 Rust 配置校验、状态和服务逻辑；
- 安装包和常驻资源占用相对较小；
- 适合托盘、通知、单实例和系统钥匙串集成；
- 前端仅通过显式 command 调用受限能力，不需要开放本地 HTTP 端口。

### 9.2 进程模型

首选将 Bridge Runtime 作为桌面应用管理的后台子进程或独立 sidecar：

- 主窗口关闭不停止 Runtime；
- Runtime 崩溃时由桌面壳有限重启并展示原因；
- 应用退出时优雅关闭适配器与 Codex App Server；
- 使用单实例锁，阻止同一配置启动两个 Bridge；
- 对同一 Bot ID 继续执行单活动连接约束。

在代码重构后，也可以将 daemon 的主要启动逻辑抽为 library，由 Tauri 进程内调用。第一阶段使用 sidecar 风险更低，能保留现有 CLI 运行方式和故障隔离。

### 9.3 模块调整

建议新增：

- `crates/bridge-runtime`：从 `bridge-daemon` 抽出的运行生命周期与状态事件；
- `apps/desktop`：Tauri 桌面应用；
- `crates/desktop-api`：供 Tauri command 使用的请求、响应和错误类型；
- `crates/secret-store`：系统钥匙串封装与凭据引用；
- `docs/desktop-app-design.md`：本文档。

现有 `bridge-daemon` 保留为无界面运行入口，并复用 `bridge-runtime`。

### 9.4 UI 与 Runtime 通信

UI 只调用白名单 command，例如：

- `get_runtime_status`
- `list_tasks`
- `read_task`
- `cancel_task`
- `list_pending_approvals`
- `resolve_approval`
- `list_projects`
- `validate_project`
- `save_project`
- `list_adapters`
- `test_adapter`
- `restart_adapter`
- `validate_config`
- `save_config`
- `export_diagnostics`

任务状态、审批和连接变化通过 Tauri event 推送。禁止提供执行任意 shell、读取任意文件或调用任意 App Server 方法的通用 command。

## 10. 数据设计

### 10.1 数据源职责

| 数据 | 权威来源 | 本地索引 |
| --- | --- | --- |
| Codex 消息正文 | Codex App Server | 默认不复制 |
| IM 与 Codex 任务映射 | Bridge SQLite | 保存 |
| 消息幂等 ID | Bridge SQLite | 保存 |
| 项目配置 | `bridge.toml` | 运行时内存副本 |
| 渠道凭据 | 系统钥匙串或现有环境 | 仅保存引用 |
| 审批状态 | 活跃请求在内存，结果写审计事件 | 保存最少结果 |
| 运行日志 | 有限滚动日志 | 不进入任务正文 |

### 10.2 建议新增表

#### `task_index`

- `thread_id`
- `platform`
- `conversation_key_hash`
- `requester_display`
- `project_id`
- `title`
- `status`
- `created_at`
- `updated_at`
- `completed_at`
- `last_error_code`

`conversation_key` 默认只保存不可逆哈希或脱敏标识，除非恢复路由确实需要原值。现有路由表继续保存运行所必需的数据。

#### `task_events`

- `event_id`
- `thread_id`
- `event_type`
- `safe_summary`
- `created_at`
- `metadata_json`

`metadata_json` 必须使用按事件类型定义的结构，禁止写入任意原始日志。

#### `approval_audit`

- `approval_id`
- `thread_id`
- `platform`
- `risk_category`
- `target_summary`
- `requester_id_hash`
- `decider_id_hash`
- `decision`
- `created_at`
- `decided_at`
- `expires_at`

完整审批范围仍由活动请求持有。审计表保存可追溯但已脱敏的摘要。

#### `config_audit`

- `revision`
- `changed_sections`
- `actor`
- `created_at`
- `result`

不保存 Secret 或环境变量值。

### 10.3 保留策略

默认建议：

- 任务索引和安全事件保留 90 天；
- 脱敏运行日志保留 7 天并限制总大小；
- 入站临时图片沿用短期临时目录，不进入长期历史；
- 审批审计保留 180 天，可由管理员缩短；
- 支持按任务、时间范围或全部清理本地索引。

删除索引不删除 Codex App Server 中的原任务，除非用户在独立且明确的流程中请求删除对应 Codex 任务。

## 11. 安全与隐私

### 11.1 信任边界

- IM 消息、引用文本、图片、日志和模型输出均视为不可信输入。
- 项目名称、描述、路径和 operator guardrail 只来自受信任配置。
- 桌面 UI 也是不可信展示层，所有敏感操作必须在 Rust Core 重新校验。

### 11.2 路径安全

- 运行时工作区只能位于 `codex.allowed_roots`。
- 项目路径必须 canonicalize 后再比较。
- UI 目录选择器不能替代后端路径检查。
- 任何越界、目录不存在或符号链接逃逸均失败关闭。

### 11.3 凭据安全

- 新增凭据写入操作系统钥匙串。
- 配置文件只保存凭据引用，不保存明文。
- UI 只展示末尾少数字符或不可逆标识。
- 日志记录凭据字段时直接丢弃，不依赖字符串替换脱敏。

### 11.4 桌面访问保护

- 系统通知不展示完整生产操作或敏感任务正文。
- 从锁屏恢复后，审批详情可要求系统身份验证。
- 复制敏感字段前显示提示；首版不提供复制 Secret。
- UI 中渲染 Markdown 时禁用任意 HTML 和远程资源加载。
- 图片只从 Bridge 创建并验证的本地媒体路径读取。

### 11.5 审批一致性

桌面端不得自行创建批准状态。所有决定必须提交到 Bridge 当前活动审批请求，由 Bridge 完成用户身份、渠道、会话、任务、令牌、过期时间和单次消费检查。

## 12. 错误与恢复

### 12.1 配置错误

应用保留最近一次有效配置。新配置只有在完整解析、路径校验和必要连通性检查通过后才能替换运行配置。

### 12.2 Runtime 崩溃

桌面壳展示退出原因并最多自动重启有限次数。连续失败后停止自动重启，避免循环，并提供诊断入口。

### 12.3 适配器断连

单个适配器断连不影响其他适配器。采用有上限的退避重连；持续失败后发送本地通知。

### 12.4 Codex App Server 不可用

停止接收新的工作请求或向 IM 返回明确的临时不可用提示。不得在 Codex 不可用时假装任务已创建。

### 12.5 桌面端关闭

关闭窗口默认缩到托盘。用户选择“停止 Bridge”或“退出”时，应显示运行中任务和待审批数量，并进行优雅关闭。

## 13. 分期计划

### Phase 0：Runtime 可观测性与重构

- 抽取可复用的 Runtime 生命周期。
- 为 daemon、适配器、Codex 和任务提供结构化状态事件。
- 增加单实例控制和有限滚动脱敏日志。
- 建立任务索引与安全事件模型。

完成标准：CLI 行为保持兼容，现有测试通过，并能从测试程序读取完整运行状态。

### Phase 1：桌面端 MVP

- Tauri 壳、托盘和开机启动选项；
- 总览与组件健康；
- 连接配置和端到端自检；
- 项目与 ACL 的结构化编辑；
- 任务列表和只读任务时间线；
- 待审批列表、系统通知和批准/拒绝；
- 脱敏日志与诊断包；
- 最近一次有效配置恢复。

完成标准：管理员无需编辑 TOML 即可完成安装、接入、验证、日常观察和审批。

### Phase 2：任务操作与审计

- 打开 Codex 任务；
- 取消任务与失败回传重试；
- 配置变更审计；
- 更完整的审批历史；
- 任务完成通知偏好；
- 按项目和人员的使用统计。

### Phase 3：高级能力

- 从桌面端向明确的来源会话发送补充消息；
- 多 Bridge 实例只读聚合；
- 企业策略模板与配置导入导出；
- 可选的团队级审计后端。

Phase 3 的远程或团队能力必须单独进行身份、加密和数据合规设计，不能直接暴露本地管理 API。

## 14. MVP 验收标准

### 安装与运行

- 首次启动能发现 Codex CLI、Node.js 和配置目录问题。
- 只能运行一个使用同一配置的 Bridge 实例。
- 关闭窗口后服务按用户设置继续在托盘运行。

### 连接

- 可配置并测试企业微信与飞书连接。
- 凭据不会出现在配置文件、UI 日志或诊断包中。
- 同一企业微信 Bot ID 不能建立两个活动连接。

### 项目与权限

- 越过 `allowed_roots` 的项目路径无法保存。
- 未配置 ACL 时保持默认拒绝。
- 企业微信与飞书的用户 ID 不共享权限命名空间。

### 任务记录

- 可以按状态、平台和项目查看经过 Bridge 的任务。
- 可以读取 App Server 中存在的任务正文和最终结果。
- 不展示隐藏分析过程和与机器人无关的群聊消息。
- App Server 正文不可用时，界面明确显示不可用原因。

### 审批

- 桌面端和 IM 卡片同时看到同一待审批请求。
- 任意一端决定后另一端同步状态。
- 非审批管理员、过期令牌和重复操作均被拒绝。
- 系统通知不泄露完整敏感内容。

### 诊断

- 可区分适配器、Codex、配置和回传错误。
- 日志和诊断包不包含 Bot Secret、令牌或 Codex 认证文件。
- 重启单个适配器不会中断其他渠道。

## 15. 测试策略

### 单元测试

- 桌面 command 的授权与输入校验；
- 项目路径 canonicalize 和 allowed root 检查；
- 凭据引用序列化；
- 日志字段级脱敏；
- 审批令牌过期和单次消费；
- 任务事件到安全时间线模型的转换。

### 集成测试

- Tauri command 到 Bridge Runtime；
- Runtime 启停与崩溃恢复；
- 适配器断线重连；
- App Server 任务读取；
- IM 卡片与桌面审批竞争提交；
- 配置原子更新和回滚。

### 端到端测试

- 企业微信消息 → Codex → 企业微信回复 → 桌面任务记录；
- 飞书话题/回复链 → Codex → 飞书回复 → 桌面任务记录；
- 普通用户发起高风险操作 → 桌面批准 → 执行 → 只读复核；
- 非管理员尝试桌面审批并被拒绝；
- 越界项目路径、重复 Bot ID 和无 ACL 配置失败关闭。

### 安全测试

- 恶意 Markdown、HTML 和远程图片；
- 日志与错误消息中的 Secret；
- 符号链接路径逃逸；
- 伪造审批 ID、任务 ID 和渠道身份；
- 重放已消费审批；
- 诊断包内容检查。

## 16. 待确认事项

以下问题不阻塞 Phase 0，但应在桌面 MVP 开发前确认：

1. 首发平台仅 macOS，还是同时支持 Windows？
2. 凭据是否统一迁移到系统钥匙串，还是长期保留环境变量模式？
3. 是否允许桌面端取消运行中的 Codex 任务？
4. 任务索引默认保留 30 天还是 90 天？
5. 审批详情是否默认要求系统身份验证？
6. Phase 1 是否需要“打开 Codex 任务”，以及 Codex 桌面端可用的稳定跳转能力是什么？

## 17. 建议结论

桌面端首版应聚焦“可安装、可配置、可观察、可审批、可诊断”。聊天记录采用 Codex 任务时间线，而不是完整 IM 历史；正文由 App Server 提供，Bridge 只保存最少索引和安全事件。技术上优先采用 Tauri sidecar 方案复用现有 Rust Core，在保持 CLI 兼容的同时逐步抽取 Runtime，避免桌面 UI 成为新的信任边界或安全旁路。
